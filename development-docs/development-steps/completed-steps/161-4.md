# 161-4 — правка сохраняет прежнее: история вместо перезаписи

**Репозиторий:** `fractera-telegrambot-starter`, `main`. **Коммит:** `82c3ddd`. **Дата:** 2026-09-08.
**Прибор `mutate-forget-161-4-5` — 13/13**, сборка `BUILD_RC=0`.

## Что делали и как

`memory_mutate` меняет известное, **не стирая прежнего**: старая строка получает статус `past`,
новая пишется `current` тем же единственным писателем. Ответ называет **обе** стороны правки —
«было Лас-Пальмас, стало Мадрид»: правка, не показавшая, что она заменила, неотличима от новой
записи, и человек не сможет сказать «нет, верни как было».

🔒 **ПРИЧИНА ПРАВКИ ЕДЕТ В `source`, А НЕ В `basis`, И ЭТО НЕ ПЕДАНТИЗМ.** `basis` уже означает «на
чём стоит предположение» (161-2). Одно слово в двух смыслах — тот класс ошибки, который проект
оплачивал трижды за три дня; поэтому у метода параметр `why`, а не второй `basis`.

🔒 **«НЕЧЕГО ПРАВИТЬ» — ОТДЕЛЬНЫЙ ИСХОД, И ОН НАЗЫВАЕТ ДРУГУЮ ОПЕРАЦИЮ.** Правка признака, у
которого значения ещё не было, — это запись; отказ так и говорит, вместо того чтобы молча создать
строку и сделать вид, что что-то заменил.

## Доказательства — две плоскости, названные в ТЗ заранее

### 1. Строки в базе

```
✓ правка без прежнего значения — это запись, а не правка: nothing-to-change
✓ исходное значение записано: personal
✓ правка назвала прежнее и новое: «Лас-Пальмас» → «Мадрид»
✓ в базе две строки: прошедшая «Лас-Пальмас» и текущая «Мадрид»
```

**Что запущено:** `node scripts/probe/mutate-forget-161-4-5.mjs`, запрос
`SELECT id, value_text, status … ORDER BY id DESC` — колонки поимённо, по закону 83.
**Что доказывает:** перезаписи не произошло; в хранилище живут обе версии с разными статусами.
**Негативный контроль:** правка несуществующего значения строк не создаёт и отвечает отказом.
**Как выглядело бы без правки:** одна строка, прежнее значение исчезло навсегда.

### 2. Чтение через дверь

```
✓ чтение отдаёт НОВОЕ значение первым: «Мадрид»
✓ прежнее значение осталось в истории: ["Мадрид","Лас-Пальмас"]
```

**Что доказывает:** тот, кто спрашивает, получает актуальное; история доступна и не мешает.
**Негативный контроль встроен:** если бы правка перезаписывала, второй строки в списке не было бы.

## Ошибки

**Найдено при написании и исправлено до отправки:** изменяющий запрос проверялся только по коду
HTTP. Слой данных отвечает `200` и `{ok:false}` на отвергнутый SQL — то есть отказ был бы засчитан
как успех, а прежнее значение осталось бы текущим рядом с новым. Теперь проверяются оба: код и тело.
🔒 **Тот же класс, что «проглоченный по закону отказ» из 143** — и он ловится только тем, что
результат чужой службы читают целиком, а не по первому полю.

## Эволюция навыков

- Правило «колонки поимённо» применено в третьем месте подряд; ошибиться в нём уже трудно — и это
  признак того, что закон работает.
- Предложение: в `use-development-steps` §5, к списку закрытия подшага, добавить строку **«ответ
  чужой службы читается целиком, а не по коду HTTP»** — сегодня это знание живёт в комментариях
  трёх разных файлов.
