# 141-2 — колонка `scope_key` лестницей, ключ охвата белым списком

**Коммит:** `5ee2220` в `fractera-telegrambot-starter`, ветка `new-step-A`. **Дата:** 2026-09-07.
**Четвёртый подшаг серии A.** Замысел — `PASSPORT.md` §3г.

## Что делали и как

`lib/facts/scope.ts` — сборка ключа охвата; четвёртая поздняя колонка `scope_key` в
`lib/facts/table.ts` с индексом `(scope_key, created_at)` и местом в образце колонок.

**Четыре решения по ходу:**

1. **Ключ собирается белым списком, как имя таблицы.** Значение уезжает и в колонку, и в условие
   запроса — попав туда без проверки, оно перестаёт быть значением и становится SQL.
2. **Кириллица переводится таблицей, а не библиотекой.** Правила транслитерации у библиотек разные;
   смена версии переименовала бы уже записанные ключи, и прошлые факты перестали бы находиться —
   молча. Без перевода «Мадрид» дал бы пустую строку, то есть «охват неизвестен» там, где человек
   его назвал.
3. **Пары сортируются по имени.** Один и тот же охват, собранный в разном порядке, дал бы две разные
   строки, и факты об одном месте перестали бы находиться друг другом.
4. **Одна непригодная пара портит весь ключ, а не выбрасывается.** Ключ из двух измерений вместо
   трёх — это **другой** охват: он шире объявленного и потому лжив. Пустой результат честнее.

## Доказательства

**1. Прибор на самой функции** (`npx tsx scripts/probe/scope-key-141-2.mjs`, `PROBE_RC=0`):

```
✓ кириллица переводится таблицей: «geo-city=madrid»
✓ две пары сортируются по имени: «geo-city=madrid|lang=ru»
✓ тот же охват в другом порядке — ТОТ ЖЕ ключ: «geo-city=madrid|lang=ru»
✓ пробелы склеиваются в дефис: «geo-city=nizhnii-novgorod»
✓ НЕГАТИВНЫЙ: попытка SQL: «geo-city=madrid-drop-table-fact-x»
✓ НЕГАТИВНЫЙ: пустое значение: «»
✓ НЕГАТИВНЫЙ: одна пара непригодна — ВЕСЬ ключ пуст: «»
✓ НЕГАТИВНЫЙ: имя измерения непригодно: «»
кавычек и служебных знаков в ключе: нет («geo-city=a-b»)
колонка scope_key объявлена в лестнице: да
колонок в образце: 12, поздних: 4
```

*Пять случаев из десяти — негативные.* Каждый выбран так, чтобы **различать** реализации: порядок
пар проверяется тем же охватом в обратном порядке, а не одним прогоном.

**2. База — лестница на таблице СТАРОГО образца** (живой слой данных, `LADDER_RC=0`):

```
ДО:    scope_key в определении: нет
ДО:    строк: 1
ПОСЛЕ: scope_key в определении: есть
ПОСЛЕ: строк: 1 — прежние на месте
запрос ПО НОВОЙ колонке нашёл: 1 строк(у)
негативный контроль (чужой охват): 0 строк — обязан быть 0
```

*Что доказывает:* колонка приезжает к таблице, созданной **до** этой правки, — то есть к тем 24,
что созданы шагом 81; данные целы, поиск по новой колонке работает.
*Как выглядело бы без лестницы:* `CREATE TABLE IF NOT EXISTS` не делает ничего на существующей
таблице — колонка появилась бы только на чистой машине, а на рабочем сервере не появилась бы
никогда. Этот класс уже оплачен в проекте дважды.

**3. Типы:** `TSC_RC=0`.

## Ошибки

- ✗ **Бэктики внутри SQL-комментария разорвали шаблонную строку** (`TSC_RC=2`). Форма таблицы —
  шаблонная строка; любой бэктик в комментарии внутри неё закрывает её. Лечение: в SQL-комментариях
  писать без бэктиков.
- ✗ **В `.mjs` нельзя писать типы TypeScript.** `tsx` смотрит на расширение, а не на содержимое —
  первый прогон прибора упал `SyntaxError`. Соседний прибор 141-1 работал только потому, что типов в
  нём не было.
- ✗ **Опять чуть не принял код `tail` за код прибора:** первая попытка запуска шла через `| tail`,
  и `PROBE_RC=0` там ничего не значил. Тот же класс, что записан про `npm run build | tail`, — и это
  **третий раз за серию**. Правило: вывод прибора в файл, код возврата сразу после команды.

## Эволюция навыков

**Что подтвердилось третий раз: конвейер с `tail` убивает код возврата.** Правило есть в
`CLAUDE.md` про сборку, но сформулировано узко — про `npm run build`. Его стоит расширить: **любой
прибор запускается с перенаправлением в файл, код берётся сразу после команды**. Пока это не
записано в навык, оно ловится случайно.
