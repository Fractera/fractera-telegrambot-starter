## Этап 1. Пересказ и решения владельца

### Просьба своими словами

Дать каждой автоматизации **короткий числовой адрес**, который человек произносит вслух, и
механизм, который решает: новое сообщение — это своя автоматизация, продолжение чужой или ссылка
на чужую.

### Решения владельца, дословно (2026-09-06)

> «В базе данных для автоматизации будем создавать числовой идентификатор, и именно по этому
> идентификатору будем работать с автоматизациями. Это простое число, которое начинается от единицы,
> на каждой новой автоматизации прибавляет одну цифру.»

> «Идентификатор присваивается каждый раз, когда пользователь начинает новое сообщение. На вкладке
> разбор запроса появляется текст: Автоматизация № 124 (предварительно) | (подтверждено) |
> (связанные с 104, 121)»

> Кейс связи: «ты создаёшь новую автоматизацию 134, записываешь как неподтверждённую, устанавливаешь
> связь с сообщением 124 и фиксируешь автоматизацию 134 как подтверждённую, которая имеет связь с
> автоматизацией 124».

> Кейс замены: «система удалит запись предварительно 128 и зафиксирует сообщение 124, будет писать
> это сообщение как продолжение сообщения 124».

### Мои допущения, названные вслух

- **я предполагаю, что** номер — это и есть `actionId` из §3 паспорта, а не второй ключ рядом с
  именем-со-временем. Два ключа разойдутся; если владелец имел в виду иначе — это меняет схему, и
  спросить надо до кода;
- **я предполагаю, что** счётчик живёт в базе (колонка автоинкремента), а не в коде: два писателя
  номеров дали бы два одинаковых номера в одну секунду;
- **я предполагаю, что** решение «связь или замена» принимает модель, а не правило: правило по
  ключевым словам («кстати», «я забыл») ошибётся на первой же живой фразе.

## Этап 2. Разведка переиспользуемого — путями

| Что берём готовым | Путь |
|---|---|
| таблицы создаются в рантайме, `CREATE TABLE` и `ALTER` | слой данных `:3300`, доказано шагом 81 |
| единственная дверь к данным | `lib/fractera/data-service.ts` → `dataFetch` |
| вкладка «Разбор запроса» | `app/[lang]/settings/_components/task-parse-section.tsx` |
| страница автоматизации и её адрес | `app/[lang]/automation/[id]`, построена 2026-09-06 |
| список и таблица автоматизаций | `app/[lang]/settings/_lib/automations.ts` — сегодня на выдуманных данных |
| связь сообщений как отношение | реестр признаков: **единственное исключение** из «таблица на признак» |
| состояния вместо неизменности | второй слой реестра, настройка `lifecycle` |

🔒 **СВЯЗЬ УЖЕ ОБЪЯВЛЕНА ОТНОШЕНИЕМ, А НЕ ФАКТОМ** (шаг 81): у неё нет значения, есть источник и
цель. Заводить для связи автоматизаций второй механизм рядом — значит развести два вида связи.

## Этап 3. Известные ограничения

| Ограничение | Что будет при нарушении |
|---|---|
| **Номер не переиспользуется никогда** | человек назвал 128 вслух до конца разбора; второй смысл у числа — молчаливая подмена дела |
| **Пропуски в нумерации законны** | следующий агент «починит» дыры и сломает уже произнесённые ссылки |
| **Предварительный номер не звучит в разговоре** | бот пообещает адрес, который через секунду исчезнет |
| **Один счётчик, в базе** | два одинаковых номера в одну секунду |
| `SELECT *` и `INSERT` без списка колонок по таблицам признаков запрещены | работает на чистой машине, путает значения на обновлённой |
| Имя таблицы собирается белым списком | ключ из свободного текста превращается в SQL |
| Слияние — переход, а не затирание | решение модели обратимо только если видно, что откуда приехало |

## Этап 4. Наблюдаемые результаты — что можно ПРЕДЪЯВИТЬ

1. «Пришло сообщение — в базе появилась строка с номером `N` и состоянием `предварительно`».
2. «Вкладка разбора показывает `Автоматизация № 124 (предварительно)`, а после разбора —
   `(подтверждено)`».
3. «Второе сообщение получило свой номер и строку связи с первым; на вкладке видно
   `(связанные с 124)`».
4. «Сообщение-продолжение сожгло свой предварительный номер: строки 128 в базе нет, а у 124 стало
   на одно сообщение больше».
5. «Счётчик после сожжённого номера продолжил со следующего, а не переиспользовал 128».
6. «Страница `/ru/automation/124` открывается по номеру, а не по имени файла».

## Этап 5–6. Подшаги, порядок и зависимости

| Подшаг | Что делает | Зависит от |
|---|---|---|
| **138-1** | таблица автоматизаций и счётчик: номер, состояние, время, ссылка на сообщение | — |
| **138-2** | выдача предварительного номера на каждое входящее сообщение | 138-1 |
| **138-3** | подтверждение номера после разбора; состояние видно на вкладке разбора | 138-2 |
| **138-4** | связь между автоматизациями: таблица отношений и показ «связанные с …» | 138-3 |
| **138-5** | слияние: сожжение предварительного номера и перенос сообщения в чужую автоматизацию | 138-4 |
| **138-6** | адрес страницы переходит с имени файла на номер; таблица списка читает базу, а не выдуманные данные | 138-5 |

🔒 **138-5 НЕ НАЧИНАЕТСЯ ДО 138-4**, и это не порядок удобства: слияние есть частный случай связи —
связь, у которой источник поглощает цель. Построив слияние первым, мы получили бы два механизма
родства вместо одного.
🔒 **138-6 ЗАКРЫВАЕТ ШАГ** и снимает выдуманные данные прототипа: пока адрес живёт на имени файла,
у автоматизации две личности.

**Дробление вертикальное:** каждый подшаг кончается строкой, которую видно снаружи, — записью в
базе или текстом на вкладке разбора.
