# Терминал агента не подключался: три дефекта, один симптом, день отладки

**Дата:** 2026-09-07 · **Подшаг:** 157-3 · **Служба:** `fractera-telegrambot` (`:3600`)
**Коммиты:** `b4cda75` · `0dee9fb` · `79b8970` · `6936071` · `f7aec4a`
**Файлы:** `server.mjs` · `proxy.ts` · `app/[lang]/terminal/_components/xterm-terminal.client.tsx`

## Симптом, каким его видел владелец

`https://chat.aifa.dev/ru/terminal` — чёрная панель, в шапке «соединение закрыто». Ни ошибки, ни
причины. Бот при этом работал целиком: напоминания, распознавание фото, часовые пояса — всё живое.

Его слова, и обе подсказки оказались верными:

> «всё это случилось после изменения работы авторизации»

> «попробуй заменить браузер чем-то другим для теста хотя бы виртуально»

**Цена:** день. Не потому, что дефект сложный, — потому что он был **немой и перемежающийся
одновременно**, а это худшая комбинация из возможных.

## Что оказалось правдой: три независимых дефекта

| № | Дефект | Как проявлялся |
|---|---|---|
| 1 | привратник авторизации исполнялся для WebSocket-запроса `/pty` | на `upgrade` уходил `GET /api/session` в службу входа, сокет рвался через 22 мс |
| 2 | **Next закрывал сокет, уже поднятый нашим мостом** | обрыв через 3 мс после приветствия, код 1006, без кадра закрытия |
| 3 | `ResizeObserver` будил сам себя через `fit()` | вкладка вставала намертво: JavaScript в ней не исполнялся вовсе |

Каждый из трёх по отдельности даёт ровно тот же экран. Поэтому починка первого не давала видимого
эффекта — и выглядела как «не помогло», хотя была верной.

## Дефект №2 — главный, и это закон, а не случай

### Механизм, прочитанный в исходнике Next 16.2.10

`node_modules/next/dist/server/next.js:313`

```js
setupWebSocketHandler(customServer, _req) {
    if (!this.didWebSocketSetup) {
        this.didWebSocketSetup = true;
        customServer = customServer || _req?.socket?.server;   // ← НАШ сервер
        if (customServer) {
            customServer.on('upgrade', async (req, socket, head) => {
                this.upgradeHandler(req, socket, head);
            });
        }
    }
}
```

Вызывается это **из обработчика первого HTTP-запроса** (`getRequestHandler()`), а не при старте.
Сервер Next берёт из `req.socket.server` — то есть из нашего же `createServer`.

`node_modules/next/dist/server/lib/router-server.js:670`

```js
const { finished, matchedOutput, parsedUrl, statusCode } = await resolveRoutes({
    req, res, isUpgradeReq: true, ...
});
// TODO: allow upgrade requests to pages/app paths?
if (matchedOutput) {
    return socket.end();          // ← закрывает НАШ поднятый сокет
}
if (finished && parsedUrl.protocol) { ... return socket.end(); }
// If there's no matched output, we don't handle the request as user's
// custom WS server may be listening on the same path.
```

Комментарий в последней строке — авторский: Next **намеренно** не трогает сокет, когда ничего не
сматчил. Но если сматчил (или если сработал middleware) — закрывает, не спрашивая, не поднял ли этот
сокет кто-то другой секундой раньше.

### Почему отказ перемежающийся — и почему это стоило дня

| Момент | Слушателей `upgrade` | Что происходит с сокетом |
|---|---|---|
| сразу после `pm2 reload` | **1** — только наш | соединение живёт, всё работает |
| после первого HTTP-запроса к службе | **2** — наш и Next | Next закрывает через 3 мс |

Браузер всегда сначала грузит страницу и только потом открывает сокет — значит **из браузера не
работало никогда**. А мои пробы с сервера я запускал сразу после перезапуска — и они **работали**.

🛑 **ИЗМЕРЕНИЕ БЫЛО НАСТОЯЩИМ И ПРИ ЭТОМ ЛОЖНЫМ.** «По петле работает, из браузера нет» — я снял это
трижды, каждый раз честно, и построил на нём целое направление: nginx, TLS, `permessage-deflate`,
маскирование кадров, заголовки Chrome. Ни одна из этих версий не была ленивой; все они были следствием
одного артефакта времени.

🔒 **ЗАКОН, КОТОРЫЙ ИЗ ЭТОГО СЛЕДУЕТ: У ВОСПРОИЗВОДИМОГО ЗАМЕРА ЕСТЬ НЕ ТОЛЬКО КОМАНДА, НО И МОМЕНТ.**
Если проба запускается после перезапуска, а живой клиент — после прогрева, это **разные условия**, и
разница между ними неотличима от разницы между клиентами. Спрашивать себя: «что произошло с системой
между моим замером и замером человека?»

### Лечение

```js
// 🔒 СОБЫТИЕ `upgrade` ПРИНАДЛЕЖИТ МОСТУ ЦЕЛИКОМ (server.mjs)
app.setupWebSocketHandler?.(server);   // Next привязывается СЕЙЧАС и ставит свой флаг
server.removeAllListeners("upgrade");  // и мы тут же снимаем его обработчик
```

Ничего не теряется: наш обработчик сам зовёт `app.getUpgradeHandler()` для всего, кроме `/pty`.
Внутренний флаг `didWebSocketSetup` после этого не даст Next привязаться второй раз.

🛑 **Снять обработчик «на всякий случай» при старте НЕЛЬЗЯ** — при старте его ещё нет. Именно поэтому
`removeAllListeners` обязан идти **после** явного вызова `setupWebSocketHandler`.

## Дефект №1 — авторизация в пути WebSocket

Матчер привратника ловил `/pty` катч-олом:

```
"/((?!_next/static|_next/image|favicon.ico|sitemap.xml|robots.txt).*)"
```

Для `upgrade`-запроса Next исполняет middleware внутри `resolveRoutes`. Привратник ходил в службу
входа (`GET /api/session`, ~20 мс), возвращал ответ — и `finished` в `router-server.js` закрывал сокет.
Двадцать два миллисекунды в трассировке — это ровно круг до `:3001` и обратно.

**Лечение:** `|pty` в отрицательный просмотр матчера. Замок при этом не ослаблен: право на терминал
проверяет дверь билета `/api/fractera/pty-ticket` (роль `architect`), а мост проверяет сам билет.

🔒 **АВТОРИЗАЦИИ НЕ МЕСТО В ПУТИ СОКЕТА, И ЭТО НЕ УДОБСТВО, А УСТРОЙСТВО.** Замок у WebSocket стоит
до соединения (одноразовый билет минутной жизни) и внутри него (проверка билета в `init`), а не в
HTTP-привратнике: тот умеет только два ответа — пропустить или **закрыть сокет**.

## Дефект №3 — наблюдатель размера будил сам себя

```js
observer = new ResizeObserver(push);   // push() зовёт fit(), fit() меняет размер хозяина
observer.observe(host);
```

Классическая петля обратной связи. Вкладка вставала намертво: `Runtime.evaluate` не отвечал 45 секунд,
консоль была пуста, DOM оставался догидратационным. **Снаружи это неотличимо от «терминал не
подключается»** — сокет не открывался просто потому, что до этой строки поток уже не доходил.

**Лечение** — две защиты, и обе нужны: размер сравнивается с прошлым (шум в доли пикселя игнорируется),
а подгонка уезжает в `requestAnimationFrame` — внутри самого обратного вызова наблюдателя её делать
нельзя.

🔒 **ЗАВИСШАЯ ВКЛАДКА ИМИТИРУЕТ ЛЮБОЙ СЕТЕВОЙ ДЕФЕКТ.** Пока главный поток заблокирован, не
исполняется ничего: ни `WebSocket`, ни `console.log`, ни таймер на 200 мс. Признак, по которому это
ловится за минуту: **инструмент отладки перестаёт получать ответ от страницы**. Если `Runtime.evaluate`
или любой другой пробник упирается в таймаут — сеть ни при чём, ищи цикл в клиенте.

## Пять опровергнутых версий

| Версия | Чем опровергнута |
|---|---|
| сессия / права: дверь билета отказывает | дверь ответила `200` с билетом; негативный контроль — несуществующая дверь дала `404` |
| nginx рвёт client→server | node-проба через nginx доставила `init`: `входящее 58 байт` → `bad-ticket` |
| виноват Chrome (маскирование, `permessage-deflate`, HTTP/2) | **проба владельца: заменить браузер** — node-клиент с сервера рвался так же |
| виноваты заголовки браузера (`Origin`, кука) | бисекция трёх проб: рвались все три, включая голую |
| процесс падает на соединении | счётчик перезапусков pm2: 218 → 218 → 218, до и после |

Каждая опровергнута **измерением**, а не рассуждением. И каждая была высказана **до** того, как я
построил прибор, — в этом и была ошибка метода.

## Прибор, который назвал виновника с первой попытки

Когда версии кончились, я перестал спрашивать «почему это могло случиться» и спросил «**кто** это
делает». Ответ дала ловушка на сокете — обёртки, печатающие стек закрывающего:

```js
const nm = (t) => process.stderr.write(
  "[pty] СОКЕТ " + t + ": " + new Error("trace").stack.split("\n").slice(1, 7).join(" << ") + "\n"
);
const origEnd = socket.end.bind(socket);
socket.end = (...a) => { nm("end"); return origEnd(...a); };
const origDestroy = socket.destroy.bind(socket);
socket.destroy = (...a) => { nm("destroy"); return origDestroy(...a); };
socket.on("end",   () => process.stderr.write("[pty] СОКЕТ: FIN пришёл СНАРУЖИ\n"));
socket.on("close", (he) => process.stderr.write("[pty] СОКЕТ закрыт, hadError=" + he + "\n"));
```

Вывод, ради которого всё делалось:

```
[pty] СОКЕТ end:  at nm (server.mjs:205:74)
   << at socket.end (server.mjs:207:30)
   << at NextCustomServer.upgradeHandler (next/dist/server/lib/router-server.js:670:31)
   << at process.processTicksAndRejections (node:internal/process/task_queues:103:5)
```

🔒 **ЛОВУШКА НА ЗАКРЫВАЮЩЕГО — ПРИЁМ, КОТОРЫЙ СТОИТ ПОМНИТЬ.** Он годится везде, где ресурс
освобождается «сам»: сокет, файловый дескриптор, дочерний процесс, таймер. Подменяешь метод
освобождения обёрткой, печатающей стек, — и вопрос «почему» превращается в вопрос «кто», у которого
ровно один ответ.

🛑 **Ловушка снята тем же шагом, что назвала имя** (`79b8970`): она подменяет методы сокета, и
оставлять её в работающем коде — значит держать в основании службы отладочную подмену.

Сохранённые пробы: `development-docs/instruments/157-3-pty-upgrade-probes.mjs`.

## Доказательства, числа до и после

| Что мерили | До | После |
|---|---|---|
| проба без `init` **после** HTTP-запроса | `CLOSE 1006` через **3 мс** | `CLOSE 1008 no-init` через **10 229 мс** |
| поход в службу входа при `upgrade` | **1** | **0** |
| слушателей `upgrade` после HTTP-запроса | **2** | **1** |
| ответ вкладки на `Runtime.evaluate` | таймаут **45 с** | отвечает |
| оболочка стартовала (`start: spawn прошёл`) | 0 | 2, и мост принимает поток кадров |

Негативный контроль у первой строки встроен в саму проверку: проба **не шлёт** `init` и потому обязана
закрыться через десять секунд с причиной `no-init`. Ответ «жива вечно» означал бы, что сломан
сторожевой срок, а не что дефект исправлен.

## Что осталось долгом

1. **`proxy.ts:44` — `(d+)` вместо `(\d+)`** в `publicAuthOrigin()`: потерянный слэш при записи файла
   через `node -e`. На домене молчит, на голом IP ломает вывод адреса службы входа.
2. **Ротация журнала моста.** `[pty]`-строки пишутся в общий `pm2`-лог без ограничения.
3. **Холодная проверка на чистом развёртывании** не делалась: правка `server.mjs` уехала в репозиторий
   службы, но сервер из `bootstrap.sh` с ней не рождался ни разу.
